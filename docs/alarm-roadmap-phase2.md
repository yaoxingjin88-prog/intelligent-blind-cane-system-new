# 报警闭环 · 二期优化点

> 一期已落地：监护人主责 / 管理端兜底；创建推管理端+家属；结案写 `handled_by`/`handled_at` 并互推 `ALARM_HANDLED`（WebSocket）。  
> 本文记录**尚未实现**、适合真机运营再做的二期事项。

## 责任回顾（一期约定）

| 角色 | 职责 |
|------|------|
| 主监护人 | 第一处理人：确认安全、联系本人、必要时报警就医 |
| 子监护人 | 同步可见、可协助结案 |
| 管理端 | 超时未处理或机构值班时的**兜底**结案 |
| 持杖用户 | 可发 SOS / 取消误报，一般不是结案人 |

## 二期优化清单

### 1. 微信订阅消息（出小程序也能收到）

- **场景**：家属未打开小程序时，摔倒 / 越界 / SOS 仍能弹出服务通知。
- **要点**：
  - 一次性订阅：`wx.requestSubscribeMessage`，引导主/子监护人授权。
  - 模板区分：新报警 vs 已处理（结案同步）。
  - 与现有 WS 并存：在线走 WS，离线走订阅消息。
- **依赖**：微信公众平台模板审核、小程序类目与用户授权。

### 2. 高危短信 / 电话（仅主监护人）

- **触发**：仅 `摔倒报警`、`SOS求助`（可选：长时间未处理的越界）。
- **对象**：优先主监护人手机号；失败可降级子监护人或管理端值班号。
- **实现方向**：短信网关（阿里云/腾讯云）或语音通知；需频控与退订。
- **注意**：勿对低电、静止等预警滥发短信。

### 3. 处理过程信息加厚

一期仅有 `handled_by`（admin/guardian）+ `handled_at`。二期可补：

| 字段/能力 | 说明 |
|-----------|------|
| `handled_by_name` / `handled_by_id` | 具体哪个监护人或哪个管理员账号 |
| `handle_remark` | 处理备注（已联系、误报、已报警等） |
| 处理时间线 | 多次跟进记录（可选独立表） |
| 管理端/小程序展示 | 列表与详情展示「谁、何时、备注」 |

### 4. 未处理超时升级

- 规则示例：摔倒/SOS **5 分钟**、越界 **10 分钟**仍未处理 → 升级：
  - 再推一次主监护人（订阅消息/短信）；
  - 同时推管理端「超时未处理」并高亮。
- 配置化阈值与开关，避免演示环境刷屏。

### 5. 报警列表与家庭圈对齐

- 小程序报警列表按**当前监护人绑定的持杖用户/设备**过滤，避免全局串数据。
- 管理端可按「家庭圈 / 监护人」筛选未处理报警。

### 6. 瞬时预警与落库统一（可选）

- 现状：低电、长时间静止多为 `GUARDIAN_ALERT` 推送，**不一定落** `alarm_record`。
- 二期可选：低电持久化；静止仅推送不落库；统一统计口径。

### 7. 误报与用户自助

- 持杖用户端：一键「我没事 / 误报」→ 结案并通知监护人（`handled_by=user`）。
- 与监护人结案共用 `ALARM_HANDLED`，文案区分来源。

### 8. 运维与审计

- 报警创建/结案审计日志（谁、从哪端、IP/设备）。
- 看板增加「平均响应时长」「监护人处理率 vs 管理端兜底率」。

---

## 建议实施顺序

1. 小程序报警按家庭圈过滤（改动小、体验立刻更好）  
2. 微信订阅消息（新报警 + 已处理）  
3. 处理备注 + 具体处理人  
4. 超时升级  
5. 高危短信/语音  
6. 误报自助、审计与看板指标
