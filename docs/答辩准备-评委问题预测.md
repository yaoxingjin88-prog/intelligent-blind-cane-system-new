## 二、技术架构类问题（高频）

### Q4：为什么选择 Spring Boot 而不是其他后端框架（如 Node.js、Python Flask）？

**参考回答要点：**

- 生态成熟：MyBatis、WebSocket、Security 等组件无缝集成
- 类型安全：Java 强类型适合 IoT 数据的复杂实体关系
- 社区资源：国内 Java 生态最完善，遇到问题容易找到解决方案
- 与硬件对接：Spring 对 MQTT、WebSocket 等 IoT 协议支持好
- 如果评委追问"Node.js 不也能做？"：可以做，但 Java 在企业级 IoT 项目中更普遍，且团队成员 Java 经验更丰富

### Q5：为什么用 Uni-app 而不是原生微信小程序开发？

**参考回答要点：**

- 一套代码可编译为微信小程序 / H5 / App，未来扩展成本低
- Vue 3 + Composition API 与管理端技术栈统一，降低学习成本
- uView Plus 组件库丰富，开发效率高
- 如果评委追问"性能有没有损失？"：Uni-app 编译后性能接近原生，对于本项目的数据展示和表单交互场景完全够用

### Q6：你的系统架构图中，管理端和小程序端如何共享同一后端？有没有遇到什么问题？

**参考回答要点：**
- 统一 RESTful API 规范，两套前端通过相同的 HTTP 接口与后端交互
- 差异点：管理端用 Axios + JWT Token，小程序端用 uni.request + 自定义 header
- 遇到的问题：小程序端的域名必须 HTTPS 且已备案，开发阶段需要配置合法域名
- 解决方案：管理端走 `localhost:8081`，小程序端走内网穿透或局域网 IP

### Q7：你的数据库是怎么设计的？为什么选择 MySQL 而不是 MongoDB 这类 NoSQL？

**参考回答要点：**
- IoT 数据有明确的结构（设备 ID、传感器数值、时间戳），适合关系型数据库
- 需要复杂的关联查询（设备-用户-告警-围栏），SQL 更高效
- 事务支持：设备绑定、告警处理等操作需要原子性
- 数据量：单设备每 10 秒一条数据，一天约 8640 条，MySQL 完全能承受
- 如果数据量激增，可以按时间分表或引入时序数据库（如 TDengine）作为补充

### Q8：你提到数据分层存储策略（30天/90天聚合），具体是怎么实现的？

**参考回答要点：**
- 30 天内保留详细传感器数据（每条记录）
- 超过 30 天按小时聚合（取平均值/最大值/最小值）
- 超过 90 天按天聚合
- 实现方式：定时任务（Scheduled Task）每天凌晨执行数据归档
- 好处：控制数据量增长，查询历史趋势时性能不受影响

## 三、WebSocket 实时通信类问题（高频）

### Q9：你的 WebSocket 是怎么实现多设备、多客户端同时在线的？

**参考回答要点：**
- 采用双层 `ConcurrentHashMap` 结构：外层 Key 为 deviceId，内层 Key 为 sessionId
- 连接建立时 `computeIfAbsent` 自动创建分组
- 断开时自动清理空分组，避免内存泄漏
- 线程安全：ConcurrentHashMap 本身线程安全，无需额外加锁
- 消息协议：JSON 格式，包含 type、deviceId、timestamp 等公共字段，支持 9 种消息类型

### Q10：WebSocket 断线重连是怎么处理的？

**参考回答要点：**
- 心跳机制：客户端每 30 秒发送 PING，服务端回复 PONG
- 如果连续 3 次未收到 PONG，客户端主动断开并触发重连
- 重连策略：指数退避（1s → 2s → 4s → 8s，最大 30s）
- 重连成功后，重新订阅该设备的消息

### Q11：为什么管理端的告警用 15 秒轮询而不是也用 WebSocket？

**参考回答要点：**
- 这是项目的一个不足之处，已在报告中承认
- 原因：管理端开发时先完成了轮询逻辑，后续优化时优先保证了小程序端的实时性
- 改进方向：管理端也可以接入 WebSocket，复用现有的 `/ws/alarm` 端点
- 轮询 vs WebSocket 的 tradeoff：轮询实现简单但有延迟，WebSocket 实时但需要维护长连接

## 四、AI 与语音交互类问题（高频）

### Q12：DeepSeek 大模型的 SSE 流式输出是怎么实现的？为什么不直接用同步接口？

**参考回答要点：**

- 同步接口的问题：AI 生成完整回复可能需要 5-10 秒，用户等待体验差
- SSE 方案：使用 Spring `SseEmitter` + 守护线程 + `HttpClient` 流式读取
- 流程：前端发起请求 → 后端创建 SseEmitter → 守护线程调用 DeepSeek API → 逐行解析 `data:` 前缀的 SSE 格式 → 通过 `emitter.send()` 逐片段推送
- 用户体验：打字机效果，首 token 延迟约 500ms-1s，后续逐字输出

### Q13：你说 AI 助手有"上下文注入"机制，具体是怎么做的？

**参考回答要点：**
- 通过 `AiContext` record 将业务数据动态注入 system prompt
- 注入的数据包括：监护人信息、视障用户档案、设备状态、传感器数据、实时地址（GPS 反地理编码）
- 例如用户问"我在哪"，AI 能区分"档案住址"和"实时位置"给出不同回答
- 这比通用的 ChatGPT 对话更有针对性，因为 AI 能感知用户的物理环境

### Q14：百度语音 STT 的音频格式转换是怎么做的？为什么不能直接传 MP3？

**参考回答要点：**
- 微信小程序录音输出 MP3 格式，百度 STT API 要求 16kHz 单声道 PCM
- 使用 JLayer 库逐帧解码 MP3
- 立体声转单声道：左右声道取平均值
- 重采样：线性插值公式 `s = src[p0] * (1 - frac) + src[p1] * frac`
- 自适应处理不同采样率的音频输入

### Q15：连续对话模式是怎么实现的？有没有遇到什么坑？

**参考回答要点：**
- 流程：TTS 播报"我在，请说话" → 自动 8 秒录音 → STT 识别 → 发送 → AI 回复 → TTS 朗读 → "请继续说话" → 下一轮
- 遇到的坑：
  - 短录音（<800ms）会误触发，需要自动过滤
  - TTS 播放时录音会录到自己的声音，需要等 TTS 播完再开始录音
  - 网络延迟可能导致对话节奏不自然

## 五、路口安全通行辅助类问题（中频）

### Q16：路口安全通行辅助的规则决策引擎是怎么设计的？

**参考回答要点：**
- 基于优先级的规则引擎，从高到低：
  1. 有车辆接近 → `WAIT`（等待）
  2. 红灯或黄灯 → `WAIT`
  3. 检测到斑马线 + 绿灯 → `PROCEED_CAUTION`（谨慎通行）
  4. 检测到斑马线但无绿灯 → `ALIGN_FIRST`（先对准方向）
  5. 未检测到斑马线 → `SEARCH_ZEBRA`（寻找斑马线）
- 优先级设计的理由：安全第一，车辆接近是最紧急的威胁

### Q17：OpenCV 是怎么检测红绿灯和斑马线的？准确率怎么样？

**参考回答要点：**
- 红绿灯检测：颜色空间转换（BGR → HSV）+ 颜色阈值分割 + 形态学操作 + 轮廓检测
- 斑马线检测：灰度化 + 边缘检测（Canny）+ 霍夫直线检测 + 平行线对筛选
- 准确率：在标准路口场景下效果较好，但复杂场景（遮挡、光线变化）仍有局限
- 这是一个基于规则的方案，未来可以考虑用深度学习（YOLO）提升准确率

### Q18：目前路口辅助是模拟的还是真实的？怎么演示？

**参考回答要点：**
- 目前是模拟模式，支持 5 种场景循环切换
- 模拟数据通过 WebSocket 推送到小程序端
- 真实场景需要摄像头采集 + OpenCV 处理，目前已有 Python 视觉模块的代码框架
- 演示时可以在小程序端的路口辅助页面实时看到红绿灯状态、斑马线检测结果、通行建议

## 六、电子围栏与轨迹回放类问题（中频）

### Q19：电子围栏的越界检测是怎么实现的？

**参考回答要点：**
- 圆形围栏：计算设备 GPS 坐标与围栏中心点的 Haversine 距离，如果距离 > 半径则判定越界
- 实时检测：每次设备上报传感器数据时，后端自动检查是否在围栏内
- 越界触发：生成告警记录 + WebSocket 推送给管理端和小程序
- 管理端可视化：高德地图上绘制 Circle 覆盖物，越界设备标红

### Q20：轨迹回放的动画是怎么实现的？为什么要用双 Polyline 叠加？

**参考回答要点：**
- 基于 `setInterval` 定时器驱动，4 档速度（1800ms/1200ms/700ms/350ms）
- 双 Polyline 方案：
  - 全路径蓝色 Polyline：展示完整轨迹
  - 已播放部分绿色 Polyline：通过 `setPath(slice(0, index+1))` 实时更新
- 好处：视觉上形成"路径渐进"效果，用户能直观看到已播放和未播放的部分
- 单个 Marker 通过 `setPosition()` 平滑移动，label 实时显示当前时间
- 进度条支持拖拽跳转，同步更新地图位置

## 七、安全性与数据保护类问题（中频）

### Q21：你的系统有哪些安全措施？

**参考回答要点：**
- JWT Token 认证：登录后签发 Token，请求时注入 Header
- 路由守卫：管理端 Vue Router `beforeEach` + App.vue 双重鉴权
- 401 拦截：响应拦截器检测 401 状态码自动跳转登录页
- API 文档：Knife4j 仅在开发环境暴露，生产环境关闭
- **诚实承认不足**：JWT 拦截器目前在开发模式下被 bypass（返回 true），密码明文存储，API Key 硬编码在配置文件中

### Q22：视障用户的隐私数据（如位置、健康信息）怎么保护？

**参考回答要点：**
- 数据库层面：敏感字段（身份证号、手机号）可以加密存储
- 传输层面：HTTPS 加密传输
- 访问控制：不同角色（管理员、监护人、视障用户）有不同权限
- 数据生命周期：超过 90 天的数据自动聚合，原始数据脱敏
- **诚实承认**：当前版本的隐私保护还不完善，后续可以引入数据加密、访问审计等功能

## 八、性能与可扩展性类问题（中频）

### Q23：你的系统能支撑多少设备同时在线？有没有做过压力测试？

**参考回答要点：**
- 当前版本：模拟器每 10 秒上报一次数据，系统稳定运行无数据丢失
- 单机瓶颈：Spring Boot 默认 Tomcat 线程池 200，WebSocket 连接数受限于内存
- 扩展方案：
  - 水平扩展：多实例部署 + Nginx 负载均衡 + Redis 共享 WebSocket 会话
  - 数据库优化：读写分离、分库分表
  - 消息队列：引入 RabbitMQ/Kafka 解耦传感器数据上报和处理
- **诚实承认**：目前没有做过正式的压力测试，这是后续需要补充的

### Q24：如果设备数量增长到 10 万台，你的架构需要怎么调整？

**参考回答要点：**
- 接入层：引入 MQTT 协议替代 HTTP 轮询，减少连接开销
- 服务层：微服务化（设备服务、告警服务、AI 服务独立部署）
- 数据层：时序数据库（TDengine/TimescaleDB）存储传感器数据
- 缓存层：Redis 缓存设备最新状态、围栏配置等热数据
- 消息队列：Kafka 处理高并发的传感器数据流

## 十一、刁钻问题预测（高难度）

### Q29：你的跌倒检测算法准确率怎么样？有没有误报？

**参考回答要点：**
- 算法：自由落体（<0.5g 持续 100ms）+ 冲击（>2.5g）+ 静止（后续加速度稳定）
- 误报场景：快速坐下、扔东西、颠簸路面
- 降低误报的方案：增加时间窗口判断、结合 GPS 速度（移动中不太可能是跌倒）
- **诚实承认**：目前是基于阈值的简单算法，后续可以引入机器学习模型提升准确率

### Q30：DeepSeek API 如果挂了或者网络断了，你的 AI 助手怎么办？

**参考回答要点：**
- 当前方案：前端会显示错误提示，用户可以重试
- 改进方案：
  - 降级策略：API 不可用时，使用本地预设的问答库（FAQ）
  - 重试机制：指数退避重试（1s → 2s → 4s）
  - 多模型备选：DeepSeek 不可用时切换到其他 LLM API（如通义千问）

### Q31：你的热力图算法 `value = count * 15 + max(0, 80 - minObstacleDistance)` 中，15 和 80 这两个参数是怎么确定的？

**参考回答要点：**
- 80：超声波传感器的有效检测范围上限（HC-SR04 有效范围 2-400cm，80cm 是近距离障碍物的阈值）
- 15：数据密度的权重系数，通过实验调整，使得密度和距离两个因子在数值上大致平衡
- 这两个参数是可以调整的，后续可以通过用户反馈和数据分析进一步优化

### Q32：你用的是高德地图，如果要适配海外市场（用 Google Maps），改动大吗？

**参考回答要点：**
- 地图 API 层面：需要替换为 Google Maps JavaScript API，地图组件需要重写
- 坐标系：高德用 GCJ-02，Google 用 WGS-84，需要坐标转换
- 后端：反地理编码 API 需要替换
- 小程序端：微信原生 `<map>` 组件在国内用微信同层渲染，海外需要换方案
- 改动量中等，但架构上是解耦的（地图逻辑集中在少数几个组件中），不会影响业务逻辑

### Q33：你的 WebSocket 有没有考虑消息丢失的问题？

**参考回答要点：**
- WebSocket 基于 TCP，本身保证有序可靠传输
- 但如果客户端断线期间有消息发送，这些消息会丢失
- 解决方案：
  - 告警消息：持久化到数据库，客户端重连后主动拉取未处理告警
  - 传感器数据：客户端重连后请求最新数据
  - 关键消息：可以引入消息确认机制（ACK）

### Q34：你项目中的 API Key（DeepSeek、百度、高德）是怎么管理的？有没有安全风险？

**参考回答要点：**
- **诚实承认**：当前硬编码在 `application.properties` 中，有安全风险
- 改进方案：
  - 使用环境变量：`@Value("${DEEPSEEK_API_KEY}")` 从环境变量读取
  - 配置中心：引入 Nacos/Apollo 统一管理配置
  - 密钥轮换：定期更换 API Key
  - 访问控制：限制 API Key 的调用来源 IP

## 十三、答辩技巧

1. **诚实面对不足**：评委更看重你对问题的认知和改进思路，而不是假装完美
2. **用数据说话**：WebSocket 延迟 < 100ms、SSE 首 token 500ms、看板加载 < 2s
3. **讲清 Why 而不只是 What**：不只是说"我用了 DeepSeek"，要说"为什么选 DeepSeek 而不是 ChatGPT"
4. **准备一个"杀手锏"演示**：AI 语音助手的连续对话模式最有冲击力，建议重点演示
5. **控制时间**：项目介绍 2 分钟，演示 5-8 分钟，问答 5-10 分钟
6. **预演至少 3 次**：确保演示流程顺畅，准备好备用方案（如 API 不可用时的降级演示）
